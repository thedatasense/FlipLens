01 — Why a dictionary at all

A 384-dimensional stream carrying far more than 384 things

The premise of every SAE is the linear representation hypothesis: a network stores a concept as a direction in activation space, and the activation is roughly a sum of the directions currently active. If that is true, and if the network tracks more concepts than it has dimensions, the directions cannot be orthogonal. They are packed — in superposition — and each individual neuron ends up responding to several unrelated things at once.

The packing is possible because near-orthogonality is cheap in high dimensions. Two random unit vectors in R384 have an expected absolute cosine of √(2/π·384) = 0.041. You can fit exponentially many directions that are all mutually near-orthogonal, so a model can afford thousands of features with only slight interference between them — as long as few are active at once. That last clause is the whole reason the autoencoder is sparse: sparsity is not a regularizer bolted on for convenience, it is the assumption that makes the decomposition identifiable.

A dictionary with more entries than dimensions is how you undo that.

What the autoencoder is being asked to do

Given activations x ∈ Rd, find an overcomplete dictionary D ∈ Rd×m with m ≫ d and, for each x, a sparse non-negative code z such that x ≈ Dz. The decoder columns are the features — the hypothesised directions the model uses. The encoder is a learned detector that guesses which columns are on. Nothing about this is specific to transformers; it is classical dictionary learning, and the modern contribution is doing it at scale on residual streams with a sparsity mechanism that trains stably.

Why this matters for FlipLens

Experiment C found the flip direction supervised: mean(donor − target) over flipped clusters. That is a difference-of-means probe, and a fair objection is that it only finds a direction because you told it what to look for. The SAE never sees a flip label during training. If a dictionary column learned purely by reconstruction lands on the same axis, the axis is a property of the representation, not of your labelling. That is the entire argument the corroboration section of the README is making.

02 — The data matrix

One question in, one 384-vector out

Before any autoencoder exists there is a matrix X, and every design decision about the SAE is downstream of what a row of it is. In sae.py a row is the residual stream at one decoder layer, at the answer position, for one phrasing of one question. Not a token average, not a pooled sentence vector — one position, one layer.

Where d = 384 comes from

train_model() defaults to dim=384, depth=6, and BabyGemmaVLM passes that straight to Gemma3TextConfig(hidden_size=dim). So the residual stream is 384-wide and there are 6 layers, indexed 0–5; --layer 1 is the second block. One cross-check falls out of that: the SAE script's own random-direction baseline reports 0.0415 / 0.0428 / 0.0423 across your three runs, and √(2/π·384) = 0.0407. Be careful what that confirms — the identity E|cos| = √(2/πd) holds for any unit direction, so the agreement verifies the dimension and nothing about the flip direction. It is a check that d = 384, not evidence about the capture. (It also means the baseline carries no information: it is a closed-form constant that the script re-derives by simulation.)

The cluster, and what a flip is

Rows are grouped into clusters: one cluster is one image-and-finding question rendered in every paraphrase in the bank. make_eval_clusters emits the original question first and then each paraphrase, so a cluster is 49 rows, not 48 — which is why original appears as a register key in the output, and why the scaled run's 73,500 rows are exactly 1,500 clusters × 49. flip_labels() marks a cluster flipped when len(set(preds)) > 1 — the model gave more than one answer to what is, by construction, the same question. Because the vision encoder returns identical features for every paraphrase in a cluster, the only thing that varies within a cluster is language. That is why a flip localises to the decoder without needing to be measured.

03 — The forward pass

Encode, keep k, decode

Your SAE is a top-k autoencoder, which is the cleanest member of the family: instead of penalising the code with an L1 term and tuning a coefficient until the sparsity comes out where you want it, you simply keep the k largest pre-activations and zero the rest. L0 is then exactly k by construction, and there is no L1 shrinkage pulling every surviving activation toward zero.

scripts/experiments/sae.py — lines 60–76the whole model
class TopKSAE(nn.Module):
    def __init__(self, d, m, k):
        super().__init__()
        self.k = k
        self.b_pre = nn.Parameter(torch.zeros(d))   # centering, shared in and out
        self.enc   = nn.Linear(d, m)                # the detector
        self.dec   = nn.Linear(m, d, bias=False)   # the dictionary, columns = features

    def forward(self, x):
        z = self.enc(x - self.b_pre)
        topv, topi = z.topk(self.k, dim=-1)
        zk = torch.zeros_like(z).scatter_(-1, topi, F.relu(topv))
        return self.dec(zk) + self.b_pre, zk

    @torch.no_grad()
    def normalize_decoder(self):
        self.dec.weight.data = F.normalize(self.dec.weight.data, dim=0)

Four details in there are load-bearing, and each is a decision you could have made differently:

  • b_pre is subtracted before the encoder and added back after the decoder. It is a learned centre for the data cloud, so the dictionary has to explain only the variation around it, not the mean. It also means b_pre receives gradient from two paths, which matters if you ever hand-write the backward pass. One wrinkle in your version: train_sae initialises it with sae.b_pre.data = Xn.mean(0), and Xn was per-dimension standardised two lines earlier, so that mean is zero by construction — the initialisation is vestigial. It reads like the standard "initialise the pre-bias to the data mean" practice, but the standardisation already did that job, so b_pre starts at zeros either way.
  • The decoder has no bias. If it did, it would compete with b_pre for the same job and the decomposition would become non-identifiable.
  • ReLU is applied after the top-k selection, not before. Selection is by raw pre-activation value; a selected unit that happens to be negative contributes nothing and receives no gradient. So the effective L0 is ≤ k, not exactly k — usually equal in practice, but worth knowing.
  • Decoder columns are normalized to unit norm. Without it, the network can shrink a column and inflate its activation (or vice versa) with no change in output, so "how strongly does feature j fire" would be meaningless, and so would any cosine you compute against the column.

The rest of the family, and why top-k

For your purpose — a corroboration run, not a dictionary you plan to publish — top-k is the right call. It removes the single largest source of arbitrariness in an SAE result (the sparsity coefficient), so nobody can ask whether you tuned λ until the flip feature appeared.

04 — Train one

Your exact recipe, running in this tab

Below is a real top-k SAE — hand-written gradients, Adam with PyTorch's defaults, decoder renormalised every 500 steps — trained on synthetic activations whose ground-truth dictionary is known. That last part is the point: on your real residual stream you cannot check whether the recovered features are the right ones, because there is no answer key. Here there is, so you can watch what "good" and "broken" look like and learn to recognise them.

sae.py — train_saePyTorch
X = acts.to(device)
mu, sd = X.mean(0), X.std(0) + 1e-6
Xn = (X - mu) / sd
sae = TopKSAE(d, m, k)
sae.b_pre.data = Xn.mean(0).clone()
opt = torch.optim.Adam(sae.parameters(), lr=1e-3)
for step in range(3000):
    gidx = torch.randint(0, n, (512,))
    recon, _ = sae(Xn[gidx])
    loss = F.mse_loss(recon, Xn[gidx])
    opt.zero_grad(); loss.backward(); opt.step()
    if step % 500 == 0:
        sae.normalize_decoder()

Note the two paths into b_pre

b_pre is subtracted at the encoder input and added at the decoder output, so its gradient has two terms with opposite signs. Autograd handles this silently; if you ever port an SAE to a framework where you write the backward yourself, this is the term people drop.

Recovery asks whether every true feature found a home in the dictionary; precision asks whether every live dictionary entry corresponds to something real. A dictionary that is too small scores low on recovery (features get merged); one that is far too large scores well on both but wastes most of its capacity on dead entries and on splitting single true features into near-duplicate shards.

The single most important lesson on this page

Set k too large and watch variance explained go to 0.99+ while recovery falls. A well-reconstructing SAE is not a correct one. Your run reports var_explained = 0.998; on its own that number says the answer-position residual stream is low-dimensional, not that the 2048 features mean anything.

05 — The frontier

Sparsity against fidelity, which is the only real dial

An SAE has exactly one fundamental trade-off, and every hyperparameter is a way of moving along it: how few features may be active (L0) against how much of the activation you can rebuild (1 − FVU). A single SAE is a point. A family of SAEs is a curve, and the curve is what you compare when you want to say one architecture or one layer is better than another.

The two curves do not peak in the same place. Reconstruction improves monotonically with k; recovery of the true dictionary peaks near the data's real sparsity and then declines. If you pick k by reconstruction alone you will systematically pick one that is too large.

On the real model you have no recovery curve, so the field substitutes proxies for the amber line. In rough order of how much they tell you:

  1. Downstream loss recovered. Splice x̂ back into the forward pass in place of x and measure how much of the model's original loss survives. This is much stricter than reconstruction MSE, because it weights errors by whether the model cares about them.
  2. Causal tests on individual features. Ablate or amplify one feature and measure the change in the output you care about. For you, that output is right there: does steering the flip-aligned feature flip the answer? This is the experiment your SAE section is currently missing, and it is the one that would turn a correlation into a claim.
  3. Interpretability scores. Automated labelling of what a feature fires on, then testing whether the label predicts activation on held-out inputs.
  4. Reconstruction quality alone. Necessary, nowhere near sufficient.

The honest state of the method

SAEs are a young and contested tool, and a corroboration argument built on one should say so. The strongest published negative results are about downstream usefulness, not about whether the decomposition exists: on sparse probing across many binary tasks, SAE-latent probes did not consistently beat logistic regression on raw activations, KNN or PCA baselines, in standard conditions or under scarcity, imbalance, label noise or covariate shift (arXiv:2502.16681); and on a steering-and-detection benchmark, SAEs were not competitive with prompting, finetuning, or plain difference-in-means (arXiv:2501.17148). Feature absorption — where a general feature quietly offloads part of its job onto a more specific one — is documented and is not fixed by tuning dictionary size or sparsity (arXiv:2409.14507).

That is not an argument against what you are doing with it. Your SAE is not being asked to be a better probe or a better steering vector; it is being asked one narrow question — does an unsupervised decomposition contain the axis a supervised method already found? — and that question is one of the things the method is genuinely good for, because failure would be informative and success does not require the dictionary to be optimal. Worth citing the negative literature anyway when you write it up, because a reader who knows it will trust the claim more if you have already bounded it.

Background reading, in the order that would be most useful here: Gao et al., Scaling and Evaluating Sparse Autoencoders (arXiv:2406.04093) — the top-k formulation you are using, plus the auxiliary loss for dead features; Rajamanoharan et al., Gated SAEs (arXiv:2404.16014) and JumpReLU SAEs (arXiv:2407.14435) — the shrinkage problem and two ways around it; Bussmann et al., BatchTopK (arXiv:2412.06410) — letting L0 vary per example; Elhage et al., Toy Models of Superposition (arXiv:2209.10652) — the geometry behind section 01.

06 — Reading a feature

Three different questions, three different statistics

Once the dictionary exists you have 2048 candidate directions and no labels. Your script asks three separable things of them, and it is worth being precise about which is which, because they can and do disagree.

QuestionStatistic in sae.pyWhat it can establish
What does it fire on?register_selectivity() — mean activation per phenomenona description; suggestive, never sufficient
Where does it point?cos = feat_dirs @ flip_dirgeometric agreement with experiment C's causal direction
What does it predict?point-biserial of per-cluster mean activation with the flip labelwhether the feature carries flip information

Nothing here is causal. A feature can point exactly along the flip axis and predict nothing (that is your results_transfer run), or predict flips strongly while pointing somewhere else entirely (that is results/sae). Only in results_gemma/sae_gemma do the two nearly coincide in a single feature — see section 08.

Point-biserial, and how much of it you actually have

The point-biserial correlation is just Pearson's r where one variable is binary; it is monotonically related to a two-sample t-test on the same data. The subtlety is not the formula, it is the sample: n in score_features is the number of clusters, not rows, and the positive class is the number of flipped clusters — 14, 26, and 81 in your three runs. With counts that small, the sampling interval on r is wide, and the maximum over 2048 features is again a selected statistic.

07 — The null you need

"Best of 2048" is not the same experiment as "one random direction"

This is the section that will change a number in your write-up. The headline SAE claim compares three quantities that are produced by three different selection procedures, and only one of them is a fair reference for the others.

QuantityHow it is computed in sae.pySelection
SAE featurenp.argmax(np.abs(cos)) over the dictionarymax of 2048
PCA baselinenp.max(np.abs(pca_dirs @ fdir)) over the top 20 PCsmax of 20
Random baselinenp.mean([abs(...) for _ in range(200)])mean of 1

The random baseline is not the null distribution of the SAE statistic. It is the null distribution of "pick one direction at random and measure it once", which is a much easier bar. The maximum of many draws is systematically larger than the mean of one, and in R384 the gap is a factor of four and a half.

How it is sampled. For a random unit vector in Rd, the squared cosine with any fixed direction is exactly Beta(½, (d−1)/2), so each draw is O(1) and no d-dimensional vector ever has to be built. That is what makes 20,000 trials × 2048 candidates instant in a browser.
What the corrected null does to your result

At d = 384: the mean of one random direction is 0.041, the expected max of 20 is 0.110 (95th percentile 0.153), and the expected max of 2048 is 0.184 (95th percentile 0.213). Your observed values are 0.737 for the SAE and 0.519 for PCA. Both clear the corrected bar by a wide margin — the finding survives intact. What changes is the sentence you write: "far above a random direction's 0.04" should become "far above the 0.21 that the best of 2048 random directions would reach by chance", which is a stronger claim precisely because it is the honest one.

Two refinements on the arithmetic. Principal components are orthonormal rather than independent, but for m = 20 in d = 384 the two nulls agree to three decimal places (0.1106 against 0.1104), so that distinction does not matter here. And the closed form √(2 ln 2m / d) overshoots the true mean by 13% at m = 2048 and by 26% at m = 20 — use it for intuition, simulate for a number.

The control that would settle it

A max-matched isotropic null is the minimum correction, and it has a real weakness: SAE dictionary columns are not isotropic draws. They are fitted to the same activations the flip direction is computed from, so both objects live in whatever subspace the answer-position residual stream actually occupies. Random directions in R384 do not.

The control that removes that objection is a placebo direction built the same way the real one is, but from clusters that did not flip. For each of 200 draws: sample the same number of non-flipped clusters as there are flipped ones (14, 26 or 81), take two distinct paraphrases at random from each, difference them, average, normalise — then take the max cosine over the dictionary exactly as before. The result is a direction with the same construction, the same norm behaviour and the same position in the data cloud as the flip direction, differing only in that it encodes no flip. That distribution is the honest null.

Not a label shuffle

The obvious version — shuffle which clusters are labelled flipped and re-run flip_direction — does not work here, and it is worth knowing why. flip_direction reads target = next(i for i, pr in items if pr != maj), and in a cluster that never flipped every prediction is identical, so next() finds nothing and raises StopIteration. More fundamentally, "the difference between the majority answer and the minority answer" is undefined when there is no minority. Shuffling is the right null for the point-biserial, where the statistic only needs a binary label per cluster and the per-cluster mean activations never move — so use a shuffle there and the placebo direction here.

Read one: the result is real

In all three runs, an unsupervised dictionary column lands far closer to the supervised flip direction than chance allows — 0.59 to 0.79 against a corrected null near 0.18. The flip axis is recoverable without flip labels. That is the claim the corroboration section needs, and it holds.

Read two: the README quotes numbers its own history already superseded

The README's paragraph — "aligns with the causal flip direction at |cosine| 0.74, clearly ahead of principal-component analysis at 0.52 … a distinct feature predicts flips (point-biserial 0.43)" — is results_gemma/sae_gemma/sae.json exactly, while the reproduce table at the bottom of the same file points readers to results_transfer/{sae,jlens}/*.json. A reader following the pointer will not find the quoted numbers.

And the gap is not just "retired probe versus scaled model". git log puts results_gemma/sae_gemma/sae.json at 8596e7c, which predates 4bedb46 — the commit that added --grounding-token and --model-steps to these two scripts. Its message is explicit about what it was fixing:

commit 4bedb46

"Both scripts called train_model() without use_ground, so they analysed a model deprived of the grounding token that carries its visual signal, and both defaulted to 1,500 training steps while the scaled model converges near 8,000. So 0.74 / 0.52 / 0.43 are the pre-fix numbers, and the same commit already recorded the post-fix ones and their honest reading: "On the scaled model both corroborations replicate directionally but weaker … Both methods measure structure in paraphrase disagreement, and this model disagrees on only 81 clusters, so there is far less to detect. The fix is to move the commit message's framing into the corroboration section and swap the four numbers.

Read three: what actually changes at scale

Best alignment falls 0.737 → 0.593 and the best flip point-biserial falls 0.433 → 0.133. Three explanations are on the table and the data here cannot separate them: (i) the author's own — there are only 81 flipped clusters out of 1,500, so there is far less signal to find; (ii) the pre-fix model was undertrained and ungrounded, and some of the 0.74 was structure in a half-blind net; (iii) 2048 features and 3000 steps underfit 73,500 rows where they comfortably fit 1,323. Only (iii) is cheap to test: rerun with --dict 8192 and a longer train_sae and see whether alignment recovers. If it does not, (i) and (ii) are the story and the honest headline is the geometric result alone.

Read four: PCA beats the SAE in one of the three runs

On the nanoVLM probe, the top-20 principal components reach 0.883 against the SAE's 0.790 — the baseline wins, from 20 candidates rather than 2048. The "edging out PCA" framing is true of the gemma run and the transfer run and false of the first. This is not embarrassing; it is the normal state of SAE evaluation, where simple baselines are competitive more often than the literature's framing suggests. It does mean the honest sentence is "on the converged probe the SAE feature is closer than any of the top 20 principal components", with the run named.

And a reproducibility flag worth chasing

run_sae_jlens_v2.sh launches sae.py and jlens.py with identical training configuration — same index, same seed 0, same --model-steps 8000, same NANO_EVAL_MAX=1500 — differing only in CUDA_VISIBLE_DEVICES. They report different flip sets: sae.json has 81 flipped clusters, jlens.json has flip_rate 0.0487 × 1500 = 73. Ten percent of the flip set is not reproducible across two GPUs at fixed seed, even with cudnn.deterministic = True. Since both "independent corroborations" are supposed to be measuring the same flips, that gap is worth one run to explain.

The strongest single fact in the three files

In results_gemma, feature 13 has |cos| = 0.737 and point-biserial +0.422 — within noise of the best predictive feature in the whole dictionary (0.433). One unsupervised feature both points along the causal axis and predicts which clusters flip. The one experiment that would close the argument

Everything in sae.py is correlational: a feature points in the same direction as the causal axis, and a feature predicts which clusters flip. Neither says the feature does anything. But the machinery to test that already exists in this repository. BabyGemmaVLM._apply_patch takes a basis argument and projects the answer position onto it:

src/babygemma/gemma_model.py — lines 113–118already written
if basis is None:
    replaced = donor
else:
    b = basis.to(x.device)
    proj = lambda h: (h @ b.T) @ b
    replaced = x - proj(x) + proj(donor)   # swap only the basis component

Experiment C passes the supervised difference-of-means direction as basis. Pass the SAE decoder column instead — feature 13's column from the gemma run — and rerun the same recovery measurement. If net recovery is comparable to experiment C's 0.98–1.00, then an unsupervised feature is not merely aligned with the causal direction, it is a causal direction, found without labels. That is a qualitatively stronger claim than the one currently in the README, and it costs one afternoon and about thirty lines.

10 — Run it

Reproducing, and one thing in the way

sae.py does not currently run

Since the package refactor (82bb2f7), train_model() no longer takes an arch keyword — there is only one architecture now, and scripts/train/train.py keeps --arch only "for run/ compatibility". But sae.py:158 still calls train_model(regime=…, seed=…, arch=arch, …), which raises TypeError: train_model() got an unexpected keyword argument 'arch'. The same call pattern appears in jlens.py:156, experiment_a.py:54, experiment_e.py:48 and scripts/legacy/eval_ground_nih.py:82. The fix is to drop the keyword (and the --arch flag) from all five.

Weights and the MedSigLIP feature cache are on Hugging Face rather than in git, so the first run needs cache/transfer_feats.pt and cache/transfer_pooled.pt in place, and gated access to google/medsiglip-448 if you rebuild them from images.

One thing the CLI does not reach: run() calls train_sae(acts, d, m=m, k=k, device=device) without steps or lr, so the SAE always trains for 3,000 steps at 1e-3 no matter what. If you want to test the underfitting hypothesis from section 08, you have to add the flags first.

A short list of worthwhile extensions, in order of value

  1. Steer the feature (section 09) — turns correlation into causation, reuses code you already have.
  2. Orient the flip direction before averaging — caveat 01. It is a two-line change to the object that every other number is measured against, and it can only raise the reported alignment.
  3. Add the placebo-direction null — a difference direction built from non-flipping clusters, which preserves the data geometry the isotropic baseline destroys; about twenty lines. Corrects two published numbers at once.
  4. Report seed variance — eight seeds of the SAE on the same model, so the max-of-2048 statistic has an error bar.
  5. Sweep the dictionary — expose --sae-steps, then --dict 8192 --topk 32 on the scaled model, to test whether the alignment drop is a real property or underfitting.
  6. Sweep the layer — the script takes --layer but only layer 1 is in the repo. Experiment C reports recovery across layers 0–4; the SAE should be run across the same range so the two methods are compared on the same axis.
  7. Log dead features and held-out reconstruction — three lines, and it closes the "is this dictionary real" question.
Where the SAE sits in the argument

The README's triangulation is: a lens-free residual patch and a Jacobian lens agree on where, a GemmaScope SAE finds a register gate on the deployed model, and this probe supplies the controlled origin. The SAE here is the bridge between the two halves — it is the method that found feature 3818 on MedGemma-4B, applied to the probe, and it recovers the same kind of object. Its job is to show that the flip axis is not an artifact of the supervised difference-of-means. On the grounded, converged model it does that at |cos| 0.593 against a corrected chance level of 0.18 — weaker than the 0.74 the README currently quotes from the pre-fix run, and still comfortably decisive.
